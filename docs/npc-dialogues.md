# NPC dialogue and building navigation

Agreed 23 September 2026. Implement named, predefined NPCs per town and building; contextual prose and spoken service choices; and lightweight memory. The player approved 2–4 sentences on arrival and 1–2 sentences per subsequent exchange. Completing a service keeps its panel open.

## Experience

Entering a building shows its named host, a short scene and greeting, and dialogue choices leading to the existing services. The current town navigation remains available. “Speak to [name]” returns from a service to the conversation; “Back to harbour” is always available. Services retain authoritative prices, confirmations, and action controls. Dialogue navigation itself costs no game time.

The Store offers trading, provisions preparation, and the existing smuggler market; Tavern offers recruitment/rest, crew care/training, and introductions; Harbour Master offers commissions and permits/navigation equipment; Shipyard offers repairs, ship exchange, and outfitting; Church offers checkpoints; Blacksmith and Weaver offer their existing catalogues. Roadmap item 4 now adds Store freight commissions; see [building commissions](building-commissions.md). Pharmacy, Fort & Garrison, and Governor now offer their implemented commission services; Church also offers monk passages and donations. Other placeholder capabilities remain unavailable. See [easy commissions](easy-commissions.md).

## NPC identities and memory

Each of the 15 towns has a fixed roster for its 14 buildings, recorded in source data. NPCs have a stable identifier, full name, occupation, personality, and voice. Names are never generated by the model. Towns have different people even when they share a building type.

Each captain stores, per NPC: visit count and last visit hour; interaction count; last successful service summary; last trade summary; and count of completed commissions. No full transcript is stored. Opening a service or returning to its conversation is not another visit. Failed actions do not create success memories. Restoring a checkpoint restores its memories, and old saves start without memories. Reopening a captain starts at the harbour; the next building entry is a return visit if recorded.

## Prose model

Request prose on building entry, choosing a service, and completing a meaningful service action. Pass the predefined identity and voice, town, conversation phase, canonical service description, bounded memory, reputation, and relevant ship/crew conditions. The model may invent atmospheric phrasing and gestures; it may not invent prices, quests, services, promises, outcomes, or past events. The game owns the choices and all mutations.

Show authored fallback prose immediately. Model latency must not disable navigation or transactions. Abort obsolete requests when the player changes location, topic, captain, screen, or AI settings; prevent stale responses from replacing newer dialogue. Limit output and request duration. Keep a small component-local cache to avoid repeated requests for identical context during a visit. Generated prose and API keys are not persisted in checkpoints.

## Deferred

- Free-text chat, full conversation transcripts, relationship quests, gifts, and romance.
- Medium/hard quest types from the [quest roadmap](quest-roadmap.md); the easy pool is implemented.
- NPC portraits and building imagery (item 8).
- Mechanical price or inventory effects from individual NPC personalities.
- Separate named smuggler contacts: the existing market is retained as a service branch; the host introduces the exchange without claiming its goods are legal.

## Acceptance

- All active services remain reachable through dialogue, with working return navigation.
- A completed action leaves its service panel selected and produces an accurate brief response.
- Names and voices are fixed across reloads; memory is isolated by captain, town, and building.
- New saves, legacy saves, and checkpoint restore work without altering economic or random state merely from talking.
- AI disabled, failure, timeout, rapid navigation, and stale responses leave the game playable with authored prose.
- Actual live model quality requires a player-configured key and is distinct from mocked API verification.

## Validation and delivery

213 tests pass across 24 files, including the complete app flow from building entry through checkpoint creation, trading, staying in the service panel, and return-visit recognition. Mocked model tests cover delayed obsolete responses, cancellation, timeouts, offline fallback, disabled AI, and per-visit caching. Memory tests cover legacy saves, separate towns/captains, and checkpoint restore. TypeScript and the production build pass; the existing Vite main-chunk size advisory remains.

Browser DOM interactions were tested with Testing Library and Happy DOM. A separate Chromium screenshot check could not run because the environment has no installed browser executable. Actual visual inspection and a live NanoGPT response remain to be checked with the player; no real API key was used.
